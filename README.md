### 01. MCU 프로그래밍

> Infineon AURIX TC275에서 HAL 없이 레지스터를 직접 설정해 GPIO, 인터럽트, 타이머, ADC를 다루는 bare-metal 펌웨어를 작성했습니다.

**실습** [AURIX_TC275](AURIX_TC275) · ShieldBuddy TC275 · AURIX Development Studio

<details>
<summary><b>상세 학습 내용</b></summary>
<br>

- **디지털 입출력**: IOCR로 핀 모드를 정하고 OMR, IN 레지스터로 LED·버튼·RGB 제어, 소프트웨어 디바운스와 에지 검출
- **레지스터 접근**: `volatile`로 레지스터·공유 변수 접근이 최적화로 생략되지 않도록 하되, 원자성이나 동기화는 보장하지 않음. 읽기·수정·쓰기 도중 인터럽트가 끼어드는 경쟁 문제와 OMR을 통한 원자적 비트 변경을 구분
- **보호 기능**: Watchdog의 실행 감시와 시간 초과 시 리셋, ENDINIT의 중요 레지스터 쓰기 보호. 보호 해제 → 레지스터 설정 → 보호 복원 순서와 해제 구간 최소화
- **인터럽트와 타이머**: STM compare 인터럽트, ERU 외부 인터럽트, SRC 설정과 ISR, ISR과 main 사이 임계 구역
- **주기 실행**: 1 ms tick 기반 비선점 다중 주기 태스크, tick ISR과 main의 작업 분리, 작업별 기준 시각으로 서로 다른 주기 관리
- **실행시간과 응답성**: STM `TIM0`로 지연 루프의 실행시간 측정, 긴 대기·폴링이 다른 작업의 실행을 늦추는 영향과 짧은 ISR의 필요성
- **주기 정확성**: 다음 타이머 비교값과 작업 기준 시각에 주기를 더해 누적 오차를 줄이는 방식, 실행 시점의 흔들림(지터)과 누적 시간 오차(드리프트)의 차이
- **센서 통신**: DHT11 단선 통신, 펄스 폭 측정, checksum, 측정 상태 머신
- **아날로그**: VADC 단발·tick trigger·scan 변환, ADC 결과 인터럽트와 ring buffer, DSADC
- **ADC 원리**: 샘플링 주파수 부족에 따른 앨리어싱, 분해능·LSB·양자화 오차, 입력 저항과 샘플링 시간의 관계. 순차 비교로 값을 결정하는 SAR와 고속 샘플링·디지털 필터를 사용하는 Delta-Sigma의 변환 방식 비교
- **신호 처리**: 이동평균, 3점 중앙값, 고정소수점 IIR 저역통과, 히스테리시스
- **측정 정확도**: 적절한 잡음이 있는 조건에서 오버샘플링을 통한 유효 분해능 개선과 출력 갱신 속도의 절충, 두 기준점의 측정값을 이용한 이득·오프셋 보정

**관련 실습** [실행시간 측정](AURIX_TC275/Lab06_stm_delay_measure.c) · [타이머 인터럽트](AURIX_TC275/Lab07_stm_isr_blink.c) · [다중 주기 태스크](AURIX_TC275/Lab09_1ms_tick_tasks.c)

</details>

요구사항 분석, 설계, 구현, 시험, 유지보수 등 소프트웨어 개발 전반의 활동과 흐름

#### 4. 소프트웨어 설계

**설계**<br>
요구사항을 구현하기 위한 구성 요소, 데이터, 인터페이스와 동작 관계를 구체화하는 활동

- **결합도**: 서로 다른 모듈 사이의 의존 정도

| 설계 표현 | 표현하는 내용 |

| 유스케이스 다이어그램 | 시스템이 제공하는 기능과 외부 참여자의 관계 |
| 클래스 다이어그램 | 클래스의 속성·연산과 클래스 사이의 관계 |
| 시퀀스 다이어그램 | 참여자 사이의 메시지와 상호작용 순서 |

**위험 기반 테스트**

발생 가능성과 영향도를 평가하여 테스트 우선순위, 적용 기법, 수행 범위와 완료 기준을 결정함

- **제품 위험**: 기능 오류, 잘못된 출력, 응답 지연 등 제품의 기능·품질과 관련된 위험
- **프로젝트 위험**: 일정 부족, 인력·장비 부족, 요구사항 변경 등 테스트 수행에 영향을 주는 위험
- 고위험 항목을 우선 검증하고 필요한 테스트 강도와 커버리지 목표를 설정

**테스트 계획의 주요 항목**

- 테스트 목표와 대상·제외 범위
- 위험에 따른 우선순위와 테스트 레벨·유형·설계 기법
- 환경·데이터·일정, 진입·완료 기준과 회귀 테스트 범위

#### 3. 테스트 조건 도출과 산출물

**설계 흐름**

요구사항·설계 등 테스트 근거 → 테스트 조건 → 커버리지 항목 → 테스트 케이스 → 실행 절차 → 실행 결과

| 항목 | 내용 |
|---|---|
| Test Basis | 테스트의 근거가 되는 요구사항, 설계, 모델 및 기준 |
| Test Condition | 확인해야 하는 기능, 특성, 상태나 동작 조건 |
| Coverage Item | 선택한 기법에 따라 도출한 분할 구간, 경계값, 조건 조합, 상태 전이 등의 확인 항목 |
| Test Case | 사전 조건, 입력·조작, 기대 결과를 구체화한 테스트 단위 |
| Test Procedure | 환경 초기화, 케이스 실행 순서, 관찰·판정 시점과 종료 절차 |

**테스트 케이스의 주요 정보**

- 고유 ID와 관련 요구사항·테스트 조건
- 사전 상태, 실행 환경·버전, 입력값·순서·타이밍
- 기대 결과와 허용 기준, 실제 결과·판정·증거 자료

테스트 조건에 설계 기법을 적용하여 필요한 케이스를 도출하고, 요구사항부터 실행 결과까지 연결 관계를 유지함

#### 4. 명세 기반·경험 기반 테스트 설계

| 기법 | 설계 기준 | 적용 예시 |
|---|---|---|
| 동등 분할(EP) | 동일한 방식으로 처리되는 입력을 그룹으로 나누고 대표값 선정 | 배터리 저전압·정상·과전압 구간 |
| 경계값 분석(BVA) | 처리 기준이 바뀌는 경계와 주변 값 선정 | 전압 범위, 통신 Timeout, 온도 임계값 |
| 결정표(Decision Table) | 여러 조건의 조합과 그에 따른 동작을 표로 정리 | IGN·램프 명령·고장 상태에 따른 출력 |
| 상태 전이(State Transition) | 현재 상태, 이벤트와 전이 조건에 따른 다음 상태 확인 | 램프·와이퍼·도어록의 상태 변화 |
| 유스케이스 테스트 | 사용자·외부 시스템의 정상·대체·예외 시나리오 구성 | 운전자 조작과 기능 수행 흐름 |
| 오류 추정(Error Guessing) | 경험과 결함 패턴을 바탕으로 취약한 상황 선정 | 빠른 ON/OFF 반복, 전압 저하 중 Reset |

**기법별 확인 사항**

- **동등 분할**: 유효·무효 입력을 구분하고 각 구간의 기대 결과를 정의
- **경계값 분석**: 입력 해상도, 비교 연산의 등호 포함 여부, 시간 측정 기준 확인
- **결정표**: 조건의 우선순위를 반영하고, 결과에 영향을 주지 않는 조건은 Don’t Care로 정리
- **상태 전이**: 유효·무효 전이, 상태별 출력, 고장 진입 및 복구 조건 확인
- **경험 기반 테스트**: 명세 기반 테스트에서 놓치기 쉬운 복합 상황과 과거 결함 유형 보완

**[CAN Timeout](python-can) 경계값 예시**

요구사항: LampCmd 메시지를 **500 ms 이상** 수신하지 못하면 통신 Timeout Fault 설정

| 테스트 케이스 | 미수신 시간 | 기대 결과 |
|---|---:|---|
| TC-BVA-01 | 499 ms | Fault 미설정 |
| TC-BVA-02 | 500 ms | Fault 설정 |
| TC-BVA-03 | 501 ms | Fault 설정 |

#### 5. 구조 기반 테스트와 커버리지

소스 코드의 실행 구조를 기준으로 테스트가 확인한 범위를 측정하고, 실행되지 않은 항목을 확인하여 테스트 케이스를 보완함

| 커버리지 | 확인 기준 |
|---|---|
| 문장(Statement) | 실행 가능한 각 문장의 수행 여부 |
| 결정(Decision) | 각 판단식의 True·False 결과를 모두 확인 |
| 분기(Branch) | 제어 흐름의 각 분기 실행 여부 |
| 조건(Condition) | 복합 판단식 내 개별 조건의 True·False 평가를 모두 확인 |
| MC/DC | 각 개별 조건이 전체 판단 결과를 독립적으로 변경하는지 확인 |
| 함수(Function) | 테스트 대상 함수의 최소 1회 실행 여부 |
| 호출(Call) | 식별된 함수 간 호출 관계의 실행 여부 |

**커버리지 = 충족한 항목 수 ÷ 전체 평가 대상 항목 수 × 100%**

**측정·해석 시 확인 사항**

- 문장 커버리지 100%만으로 모든 분기나 조건을 확인했다고 판단할 수 없음
- 함수가 실행되어도 내부의 모든 분기와 해당 함수로 연결되는 모든 호출 관계가 실행된 것은 아님
- `&&`, `||`의 단락 평가에서는 뒤쪽 조건이 평가되지 않을 수 있으므로 실제 평가 여부를 구분
- 도달 불가능한 코드와 제외 항목은 근거를 기록하고 측정 범위를 명시함
- 커버리지 100%는 선택한 기준의 충족을 의미하며, 결함이 없음을 보장하지 않음

#### 6. 테스트 환경

| 환경 | 테스트 대상과 구성 | 주요 확인 사항 |
|---|---|---|
| [MIL](Simulink) | 제어 모델과 차량·플랜트 모델을 PC에서 시뮬레이션 | 제어 로직, 알고리즘 및 요구사항 |
| [SIL](Simulink/03_PI제어기_C코드생성) | 생성하거나 직접 작성한 소프트웨어 코드를 PC에서 실행 | 코드 동작, 인터페이스, 단위·통합 동작 |
| PIL | 실제 프로세서·MCU에서 코드를 실행하고 주변 환경은 시뮬레이션 | 타깃 의존성, 연산 시간, 컴파일러 영향 |
| HIL | 실제 ECU를 실시간 시뮬레이터 및 I/O 장비와 연결 | 실제 입출력·통신, 타이밍, 고장 주입과 통합 동작 |

- **환경 관리**: 대상 버전, 설정값, 입력 데이터, 계측·로그 조건을 함께 관리하여 결과의 재현성 확보
- **테스트 자동화**: 반복 실행, 데이터 생성, 환경 구성, 정적 분석, 결과 수집과 보고 등에 적용

#### 7. 실행 결과와 결함 관리

| 기록 항목 | 주요 내용 |
|---|---|
| 실제 결과 | 실행 중 관찰한 출력값, 상태, 동작 및 수행 시간 |
| 테스트 판정 | 기대 결과와 비교한 Pass·Fail 또는 실행 차단 상태인 Blocked |
| 실행 로그 | 실행 시각, 대상 버전, 환경, 절차와 증거 자료 |
| 이슈 보고서 | 재현 절차, 기대·실제 결과의 차이, 영향 범위와 후속 조치 |

- 관찰한 사실과 판정을 구분하여 기록
- 예상과 다른 결과가 발생하면 소프트웨어 결함, 환경, 데이터, 절차 및 기대 결과의 오류 가능성을 분석

**심각도와 우선순위**

- **Severity**: 결함이 제품과 사용자에게 미치는 영향의 크기
- **Priority**: 수정과 검증을 수행해야 하는 우선순위

**재시험과 회귀 테스트**

| 구분 | 목적 | 주요 대상 |
|---|---|---|
| 재시험(Retesting) | 발견된 결함의 수정 여부 확인 | 이전에 실패한 케이스와 관련 조건 |
| 회귀 테스트(Regression Testing) | 변경으로 인한 기존 기능의 문제 발생 여부 확인 | 변경 영향이 있는 기존 테스트 범위 |

**완료 보고 및 결과 보관**

- 실행 현황, 커버리지, 미해결 결함, 계획 대비 편차와 잔여 위험 정리
- 테스트 케이스·스크립트·데이터·환경 설정과 결과를 해당 버전에 연결하여 보관

| 상태 전이 | 램프, 와이퍼, 도어록, 고장·복구 동작 | 초기 상태, 이벤트, 전이 조건과 다음 상태 |

| 결정 커버리지 | 커브 구간의 설정 속도 제한 | 중첩 판단식마다 True·False 결과 |
| 조건 커버리지 | 안전벨트 경고음, 차선이탈 경고 조건 | 개별 조건의 True·False 평가와 단락 평가 |
| MC/DC | AEB 제동 요청, OTA 설치 허용 조건 | 조건별 독립 영향을 확인하는 테스트 쌍 |
| 함수·호출 커버리지 | 램프 제어기의 함수 구성과 호출 관계 | 실행된 함수·호출 관계 및 누락 항목 |

**MC/DC 테스트 케이스 예시**

교재의 AEB 제동 요청 조건: `D = A && B && C`

- **A**: 차량 주행 중
- **B**: 물체 감지 확정
- **C**: 운전자 개입 없음
- **D**: 제동 요청 여부

| 테스트 케이스 | A | B | C | 기대 결과 D |
|---|---|---|---|---|
| T1 | True | True | True | True |
| T2 | False | True | True | False |
| T3 | True | False | True | False |
| T4 | True | True | False | False |

| 확인할 조건 | 비교할 테스트 쌍 | 확인 내용 |
|---|---|---|
| A | T1 ↔ T2 | B·C를 유지하고 A만 변경했을 때 D의 변경 여부 |
| B | T1 ↔ T3 | A·C를 유지하고 B만 변경했을 때 D의 변경 여부 |
| C | T1 ↔ T4 | A·B를 유지하고 C만 변경했을 때 D의 변경 여부 |

각 조건이 전체 판단 결과에 미치는 독립적인 영향을 비교 쌍으로 확인함

### 11. 임베디드 인터페이스 회로

> 센서·MCU·부하 사이의 신호 조절, 구동 및 보호 회로를 학습했습니다.

<details>
<summary><b>상세 학습 내용</b></summary>
<br>

#### 1. 전압·전류와 RC 회로

- **전압·전류·저항**: 두 지점 사이의 전위차, 전하의 흐름, 전류 흐름을 제한하는 관계를 옴의 법칙 `V = IR`로 확인
- **GND**: 회로에서 전압을 판단하는 기준점. 비절연 회로 사이의 신호 연결에서는 기준 전위와 전류가 돌아오는 경로를 함께 확인
- **커패시터**: 전하를 저장하며, 충전·방전 과정에서 전압 변화가 발생
- **RC 시정수**: `τ = RC`로 충전·방전의 시간 특성을 결정. RC 저역통과 필터는 고주파 잡음을 줄이며, 시정수가 커질수록 신호 변화에 대한 응답이 느려짐

#### 2. 회로도 읽기

- **부품 식별**: 저항·커패시터·다이오드·트랜지스터·IC의 기호, 부품 번호와 값, 극성 및 단자 구분
- **연결 관계**: 접속점과 단순 교차선을 구분하고, 같은 네트 이름으로 연결된 지점을 확인
- **전류 경로**: 전원에서 부하를 거쳐 돌아오는 경로를 추적하고, 스위치·트랜지스터의 상태에 따른 변화 확인
- **신호 경로**: 센서 → 입력 회로 → MCU, MCU → 구동 회로 → 부하의 연결 관계 확인

#### 3. GPIO의 전기적 특성

| 구분 | 동작 및 역할 |
|---|---|
| 푸시풀 출력 | 출력단의 트랜지스터로 High와 Low를 직접 구동 |
| 오픈드레인 출력 | Low를 구동하거나 출력을 해제하며, 풀업 저항으로 High 형성 |
| 풀업·풀다운 | 입력이 연결되지 않거나 구동되지 않을 때 기본 논리 상태를 정해 부유 입력 방지 |
| 소싱·싱킹 | 핀에서 부하로 전류를 공급하는 방식과, 부하에서 핀으로 전류를 받아들이는 방식 |

- **논리 전압**: 출력의 High·Low 보장 범위와 입력의 High·Low 판정 기준을 비교
- **노이즈 마진**: 출력 보장 전압과 입력 판정 기준 사이의 여유로, 신호에 허용되는 잡음 범위를 판단
- **허용 범위**: 핀별 전압·전류뿐 아니라 핀 그룹과 패키지 전체의 제한도 확인
- **데이터시트 해석**: 전원·온도·부하 전류 등 적용 조건과 최소·최대 보장값을 확인. 절대 최대 정격은 정상 동작이 보장되는 조건으로 사용하지 않음

#### 4. 센서 입력과 신호 조절

| 회로 | 역할 |
|---|---|
| 분압 회로 | 입력 전압을 MCU의 허용 범위에 맞추거나, 저항형 센서의 변화를 전압으로 변환 |
| RC 필터 | 센서 신호에 섞인 고주파 잡음과 급격한 변화를 줄임 |
| 버퍼 | 높은 입력 임피던스로 센서의 부담을 줄이고, 뒤쪽 회로를 구동 |
| 증폭 회로 | 작은 센서 신호를 ADC 입력 범위에 맞게 확대 |
| 슈미트 트리거 | 상승·하강 시 서로 다른 판정 문턱을 사용해 경계 부근의 반복 전환을 줄임 |

- **부하 효과**: 센서의 출력 임피던스와 연결 회로의 입력 임피던스에 따라 측정 전압이 달라질 수 있음
- **증폭 시 고려 사항**: 신호와 함께 잡음·오프셋도 커질 수 있으므로 증폭률과 연산증폭기의 입출력 범위를 함께 확인

#### 5. 트랜지스터와 부하 구동

GPIO의 전압·전류 범위를 넘는 부하는 구동 소자를 통해 제어하며, 부하에 필요한 전류는 전원과 구동 소자를 통해 공급함

| 구동 소자 | 역할 및 고려 사항 |
|---|---|
| BJT | 베이스 전류로 부하 전류를 제어하며, 베이스 저항과 충분한 구동 전류를 고려 |
| MOSFET | 게이트·소스 사이 전압으로 도통을 제어하며, 구동 전압·도통 저항·게이트 충방전을 고려 |
| 드라이버 IC | 여러 부하를 구동하거나 MOSFET 게이트의 충방전에 필요한 전류를 공급 |

- **LED**: 순방향 전압과 목표 전류에 맞춰 직렬 저항을 선정
- **모터**: 정상 운전 전류와 기동 전류를 구분하고, 구동 소자의 전류 용량과 발열을 확인
- **릴레이·모터 등의 유도성 부하**: 전류 차단 시 과도전압이 발생하므로, 플라이백 다이오드 등으로 저장된 에너지가 방출될 경로를 확보

#### 6. 보호 회로와 절연

| 고장·외란 | 주요 대응 |
|---|---|
| 과전류 | 직렬 저항·퓨즈·PTC 등을 이용한 전류 제한 또는 차단 |
| 과전압·서지 | 클램프 다이오드·제너 다이오드·TVS 등을 이용한 전압 제한 |
| 전원 역접속 | 다이오드·MOSFET 등을 이용한 역방향 전류 차단 |
| 정전기 방전 | 커넥터 주변의 적합한 보호 소자를 통해 방전 전류 우회 |
| 과열 | 소비전력·온도 정격과 여유를 확보하고, 필요 시 출력 차단 |

- **보호 소자 선정**: 고장 전압·전류의 크기, 지속시간과 에너지를 기준으로 소자의 정격과 응답 특성을 확인
- **전기적 절연**: 광커플러·릴레이 등을 통해 양측의 직접적인 전기 연결을 분리하고, 접지 전위 차이와 고장 전파의 영향을 줄임
- **절연 구성**: 양측 전원과 접지 구성을 확인하고, 절연 장벽을 우회하는 연결이 생기지 않도록 구성
- **차량 전원 환경**: 시동 시 전압 강하, 발전기 충전 중 배터리 분리에 따른 과도전압, 배터리 역접속 등을 함께 고려
